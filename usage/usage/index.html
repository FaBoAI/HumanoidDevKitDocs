LeRobot 操作マニュアル (FaBo Otter / Jetson AGX Thor)

日常の「起動 → 収録 → 学習 → 評価 → 実機」の操作をまとめた実用マニュアル。 環境の新規構築は docker-lerobot リポジトリの SETUP.md、各ポリシーの深い知見は 本リポジトリの各スキル (*-training-skills/) を参照。

1. 起動

1
cd ~/docker-lerobot && sh run.sh

起動時にセルフチェックが走る: can0 自動up / torch+CUDA / プラグイン3種 / site-packages パッチ / 音声ガイド / ディスプレイ。全てOKならそのまま作業開始。 ホスト側では can0 はブート時に自動 up される (host/can0.service 導入済みの場合)。

  • コンテナ内の作業ディレクトリは /home/jetson/Otter
  • データセット・学習出力・HF キャッシュ・較正はホストと共有 (バインドマウント)

2. データセットの切替 (最初に1回)

1
2
sh tool/set_dataset.sh humanoid_test100_640    # 全スクリプトがこの名前を使う
sh tool/set_dataset.sh                          # 現在の設定を確認

設定は datasets/current.env に保存され、ホスト/コンテナ共通・再起動後も有効。 優先順位: コマンド引数 > 環境変数 (DATASET_ROOT / DATASET_NAME) > current.env > 既定値。

⚠️ 既存データセットと同名で録り直すと、旧データで学習したモデルとの対応関係が 分からなくなる。録り直しは新しい名前を推奨。

3. データ収集

1
2
3
sh record/run_dataset.sh 30        # 新規データセットに30エピソード (20秒/ep)
sh record/run_dataset_add.sh 10    # 既存データセットへ追加
TASK="Pick up the cup" sh record/run_dataset.sh 30   # タスク文を変える場合
  • 音声「Recording episode N」で収録開始。エピソード後は自動で原点復帰し、 次のアナウンスまでフォロワーは動かない (この間にシーンを変更する)
  • キー操作: n=次へ / r=撮り直し / q=終了
  • シーン頑健性のため、エピソード毎に対象物の位置・向きを変えて録るのが推奨 (単一シーン収録はオフライン評価が良くても実機で動かない — test080 の教訓)

4. 学習

ポリシー コマンド 実測レート 15〜20K の所要
ACT sh train/run_train_act.sh 17.4 step/s (batch2) 約10分 (10K)
SmolVLA sh train/run_train_smolvla.sh 4.2 step/s (batch8) 約80分 (20K)
GR00T sh train/run_train_groot.sh 1.1 step/s (batch4) 約3.8時間 (15K)
π0.5 sh train/run_train_pi05.sh 0.38 step/s (batch4) 約11時間 (15K)
VLA-JEPA sh train/run_train_vlajepa.sh 0.52 step/s (batch4) 約13.5時間 (25K)
FastWAM sh train/run_train_fastwam.sh 0.33 step/s (batch4) 約14時間 (15K)
  • ステップ数変更: STEPS=30000 BATCH=8 sh train/run_train_smolvla.sh
  • 追加学習 (継続): sh train/run_train_{act,groot,lingbotva}_resume.sh <総ステップ数>
  • 夜間・不在時はホスト端末の nohup から (コンテナ内 nohup は exit で死ぬ): 
    1
    nohup sh /home/jetson/Otter/train/run_train_trio.sh > /home/jetson/Otter/logs/train_trio.log 2>&1 &
    (ACT → SmolVLA → GR00T → π0.5 の連続実行。1つ失敗しても次へ進む)
  • 新ポリシー・新レシピは夜間投入前に STEPS=10 でスモークテスト必須
  • 出力先は outputs/train/<policy>_<データセット名>/。同名が既にあると .bak.日時 に自動退避される (ディスクを食うので不要になったら削除)

5. オフライン評価 — 実機前の関門

1
python tool/eval_smolvla_offline.py    # 冒頭の CKPT/DS_ROOT を対象に書き換えて実行
  • 方向一致 ≥ 0.85 が実機投入の関門。不合格なら実機に載せない (LingBot-VA 0.66・Evo-1 0.64〜0.75 はこの関門で見送り → 事故ゼロ)
  • 合格の目安: SmolVLA は MAE ≤1・方向一致 ≈1.0 が出る
  • ただしオフライン合格 = 実機で動く、ではない (シーン一致は別の関門 → §6)

6. シーン確認 → 実機推論

1
2
3
4
5
python tool/check_scene.py             # 今のシーンでモデルが動くか (70%以上でOK)
sh infer/run_infer_smolvla.sh 30       # SmolVLA: RTC (実機最強の実績)
sh infer/run_infer_groot.sh 30         # GR00T: sync 固定 (RTC は暴走のため禁止)
sh infer/run_infer_act.sh 30           # ACT: sync + n_action_steps=30
sh infer/run_infer_pi05.sh 20          # π0.5: sync 既定・初回は20秒から
  • モデルは set_dataset.sh の設定に連動して自動選択 (明示指定は POLICY_PATH=)
  • 対象物を学習時と同じように配置してから実行 (check_scene が低いと動かない)
  • 初回の新ポリシーは必ず低 duration (20秒)・Ctrl+C 即応体制で

7. トラブル早見

症状 対処
カメラ READY にならない 冷却 + sudo ip link set mgbe0_0 down && sleep 2 && sudo ip link set mgbe0_0 up
リーダー無応答 5V電源を確認 → python tool/check_leader_ping.py
グリッパが固まる リーダーの手を開くと約1秒で自動復旧。履歴: outputs/gripper_guard.log
ディスク不足 古い outputs/train/*.bak.* と docker image prune から削る
実機でほぼ動かない check_scene.py でシーン一致を確認 → 対象物の配置を学習時に合わせる

8. 絶対の掟

  1. PYTORCH_CUDA_ALLOC_CONF を設定しない (Thor でリーク/激遅化)
  2. kill -9 しない — SIGTERM で止める (NvMap リークは再起動でしか直らない)
  3. HF_HUB_DISABLE_XET=1 (スクリプトに設定済み — 自前実行時も忘れずに)
  4. 夜間ジョブはホスト端末の nohup / 実行中スクリプトの編集は反映されない
  5. むやみに再キャリブレーションしない — 較正やり直し=座標系再定義で、 既存データセット・学習済みモデルと非互換になる
